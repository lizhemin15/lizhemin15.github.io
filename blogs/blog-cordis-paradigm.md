# 时空可组合之道

## 缘起

今天开始研究DeepSeek的一篇论文——《A Programming Paradigm for Spatiotemporal Composability》。这篇论文想解决一个很根本的问题：**动态组合**。

什么是动态组合？简单说就是：软件运行时，能不能随时加功能、减功能，而不用重启？

想想你用的VSCode插件：装了一百个插件，想禁用其中一个，往往得重启整个VSCode。为什么？因为插件装上去之后，它对环境做的修改（注册事件、分配资源、改变状态）没有被记录下来，也没有"撤销"按钮。

再想想AI Agent框架：Agent在运行过程中，可能会加载新的工具、学习新的能力。如果这些能力不能被安全地卸载，内存泄漏、资源占用就会越来越严重。

这就是动态组合的困境。

---

## 一、问题：为什么现在的软件做不到"动态组合"？

### 时间维度：卸载不可逆

想象一下你在玩乐高积木。你搭了一个房子，然后又加了一块砖。现在你想把这块砖拿掉——很简单，直接拔下来就行。

但软件不一样。软件里的"砖块"一旦装上，就像用胶水粘住了。你想拆掉？要么连墙一起拆（重启进程），要么就留在那里占地方。

为什么？因为软件没有记录"这块砖是怎么装上去的"。没有安装说明书，自然就没有拆卸指南。

论文里管这个叫**时间可组合性**：组件卸载的时候，它对共享环境的修改必须能够完全撤销。

### 空间维度：依赖无契约

再想象一下，你写了一个插件A，它需要调用插件B的功能。你怎么找到B？怎么确认B能提供你需要的功能？

VSCode的做法是：你可以声明`extensionDependencies`，告诉系统"我需要插件B"。但实际上，前100个热门插件里只有7个用了这个功能。而且，就算声明了依赖，调用B的功能时返回的是`any`类型——没有任何结构化的保证。

这就好比你去餐厅点菜，菜单上写着"需要食材B"，但你拿到手的是一个黑盒子，不知道里面是什么，也不知道符不符合你的口味。

论文里管这个叫**空间可组合性**：组件之间必须能够声明、发现、解析彼此的依赖，而且这种依赖关系必须是可验证的。

### 静态系统的局限

你可能会说："效应系统不是已经解决了副作用追踪的问题吗？协效应系统不是已经解决了上下文需求的问题吗？"

先解释一下这两个概念：

**效应系统（Effect Systems）** 是一种编程技术，用来追踪程序中的"副作用"——也就是那些会影响外部世界的操作，比如读写文件、发送网络请求、修改数据库。想象一下你在写一个函数，如果这个函数只是做数学计算，那它是"纯净的"；但如果它还会打印日志、修改全局变量，那它就有副作用。效应系统就是帮你记录和控制这些副作用的工具。

**协效应系统（Coeffect Systems）** 则是反过来——它追踪程序需要什么"上下文"才能运行。比如一个函数可能需要读取当前用户的配置、当前的地理位置、或者某个数据库连接。协效应系统会检查这些依赖是否满足，确保程序不会因为缺少必要的信息而崩溃。

没错，但这些系统都是**静态的**。它们在编译时就确定了作用域、确定了上下文。而动态组合要求这些保证对**运行时到达和离开的组件**成立——部署后加载的插件，没有固定的词法作用域；运行时配置产生的依赖，无法在编译时预判。

解释一下"词法作用域"：这是指代码中变量的作用范围是由代码的书写位置决定的。比如一个函数内部定义的变量，只能在这个函数内部访问。但动态加载的插件，它的代码是在运行时才被加载进来的，编译器无法预先知道它会用到哪些变量、会修改哪些状态。

所以论文作者说：与其给静态类型系统加更多注解，不如把效应和协效应的概念结构具体化，让运行时可以直接操作它们。

## 二、理论：可逆效应与响应式协效应

这一部分有点抽象，我会尽量用比喻来解释。

### 可逆效应：给每个副作用配一个"撤销按钮"

想象你在用Photoshop修图。你做了三步操作：调亮度、加滤镜、锐化。现在你想回到原始图片——怎么办？

如果你记得每一步的操作参数，可以手动反向调整。但如果步骤很多呢？如果中间还穿插了其他操作呢？

Photoshop的做法是：给你一个"历史记录"面板，每一步操作都记录下来，你可以点击任意一步回到那个状态。

论文的想法类似：**每个副作用都应该携带一个"撤销操作"**。当你执行一个副作用时，不仅执行它本身，还要把它的撤销操作存起来。等到需要恢复的时候，按顺序执行这些撤销操作就行了。

用数学语言说：

```
∂Γ ≔ Γ × (Γ → Γ)
```

别被公式吓到，拆开看很简单：
- `γ : Γ` 是当前状态（比如Photoshop的当前画面）
- `φ : Γ → Γ` 是累积器，也就是所有已执行撤销操作的组合（比如"先撤销锐化，再撤销滤镜，最后撤销亮度调整"）

初始状态是 `(γ₀, idΓ)`，意思是"当前状态是原始画面，还没有做任何操作"。

**追踪变换** `trackΓ`：当你做一个操作时，更新状态，同时把对应的撤销操作加入累积器。

**恢复变换** `recoverΓ`：执行累积器里的所有撤销操作，把状态恢复到初始值，然后清空累积器。

论文证明了一个重要性质：追踪是幺半群同态。这意味着你可以把多个操作当作一个整体来推理，不用担心顺序问题。

解释一下**幺半群同态**：
- **通俗说**：就像你整理房间，不管你是先叠衣服再放书，还是先放书再叠衣服，最终结果都是房间变整洁了。这两个操作可以"合并"成一个大操作——"整理房间"。
- **专业说**：幺半群是一种数学结构，满足结合律（(a+b)+c = a+(b+c)）。同态是指两个结构之间保持运算关系的映射。这里的意思是：追踪变换能把多个独立操作"打包"成一个复合操作，而且这个打包过程保持了运算的规律性——你可以安全地重组操作顺序，不会影响最终结果。

### 响应式协效应：让组件"感知"环境变化

想象你在订阅一个新闻服务。你告诉它："我只关心科技新闻。"然后，当有新的科技新闻发布时，它会通知你；当有体育新闻时，它不会打扰你。

这就是响应式协效应的核心思想：**组件声明自己需要什么，运行时负责通知它什么时候该激活、什么时候该停用**。

具体来说：
- **激活**：环境满足了组件的依赖条件，组件应该开始工作
- **停用**：环境不再满足依赖条件，组件应该停止工作
- **中性**：环境变化与组件无关，组件继续待命

论文把这个概念形式化为"协效应规范"，并证明它可以与可逆效应统一在一个框架下。

解释一下**协效应规范**：
- **通俗说**：就像你去餐厅吃饭，服务员会给你一张菜单，上面写着"本店提供川菜、粤菜、日料"。你根据自己的口味选择——这就是你的"需求声明"。餐厅根据你的选择来决定给你上什么菜。协效应规范就是组件给运行时的"菜单"，告诉它自己需要什么，运行时据此决定何时激活该组件。
- **专业说**：协效应规范是一个函数 `D → 𝒟`，它将依赖环境 D 映射到类型化的依赖需求集合 𝒟。运行时通过比较当前环境与组件声明的需求，来判断组件应该处于激活、停用还是中性状态。

### 上下文范式：统一的"舞台"

如果把可逆效应比作"演员的动作"，把响应式协效应比作"观众的反应"，那上下文范式就是**同一个舞台**。

```
C ≔ Γ × (Γ → Γ) × D
```

- `Γ` 是状态（舞台上的布景）
- `Γ → Γ` 是撤销操作（换布景的工具）
- `D` 是依赖注册表（演员名单和联系方式）

所有效应和协效应都通过这个统一上下文中介。论文证明了一个重要的独立性性质：不同组件的效应交错而不互相干扰，协效应的判断互不影响。

这意味着什么？意味着你可以安全地并行加载多个插件，不用担心它们会互相踩脚。

## 三、实践：DeepSeek Harness如何落地

理论说完了，现在来看看DeepSeek Harness是怎么把这些想法变成代码的。

### Context：服务的"总调度台"

Context是整个框架的核心。它不是一个简单的对象，而是一个**代理（Proxy）**——当你访问它的属性时，它会自动去查找对应的服务。

解释一下**代理（Proxy）**：
- **通俗说**：就像你公司的前台接待员。你想找某个部门的人，不需要知道具体是谁、在哪间办公室，只需要告诉前台你要找什么部门，前台会帮你联系。代理就是这样一个"中间人"——你访问它的属性时，它不会直接返回值，而是去查找对应的服务并返回给你。
- **专业说**：代理模式是一种设计模式，它提供一个占位符来控制对原始对象的访问。在DeepSeek Harness中，Context使用代理来延迟加载和动态查找服务，使得服务可以在运行时注册和发现。

```typescript
export class Context {
  readonly fiber: Fiber
  readonly events: EventsService
  readonly reflect: ReflectService
  readonly registry: RegistryService
}
```

关键设计：

1. **继承链**：`ctx.extend()`可以创建子上下文，继承父上下文的所有服务，但可以覆盖特定服务。这就像公司里的部门——子公司继承母公司的制度，但有自己的特殊规定。

2. **Fiber绑定**：每个Context绑定一个Fiber。Fiber的状态决定了Context的可用性。当Fiber进入UNLOADING状态时，Context上的服务会自动失效。

### Fiber：可逆效应的"执行单元"

Fiber是承载副作用的最小单元。它记录了所有注册的服务、监听的事件，并在销毁时反向执行这些操作。

解释一下**Fiber**：
- **通俗说**：就像你手机上的一个"任务卡片"。每个卡片代表一个独立的工作单元——比如加载数据、处理事件、调用API。当你完成任务后，把卡片翻过来，上面写着"如何撤销这个任务"。这样，如果你想取消这个任务，就按照卡片上的说明一步步撤销。
- **专业说**：Fiber是一个轻量级的并发单元，类似于线程但更高效。在DeepSeek Harness中，Fiber不仅管理异步执行，还负责追踪所有副作用和清理操作，确保资源能够被正确释放。

```typescript
export class Fiber<T = any> extends Promise<T> {
  state: FiberState = FiberState.PENDING
  private disposers: DisposableList = new DisposableList()
  
  async dispose(): Promise<void> {
    if (this.state === FiberState.DISPOSED) return
    this.setState(FiberState.UNLOADING)
    // 反向执行所有注册的清理函数
    await this.disposers.dispose()
    this.setState(FiberState.DISPOSED)
  }
}
```

关键设计：

1. **DisposableList**：使用双向链表管理清理函数，确保注册顺序与销毁顺序相反（LIFO）。这就像叠盘子——最后放上去的最先拿下来。

解释一下**DisposableList**和**LIFO**：
- **通俗说**：想象你在厨房做饭，你先拿锅，再拿铲子，最后拿盘子。做完饭后，你要收拾——你会先放盘子，再放铲子，最后放锅。这就是LIFO（后进先出）：最后拿的东西最先放回去。DisposableList就是这样一个"栈"结构，确保资源释放的顺序与分配的顺序相反。
- **专业说**：DisposableList是一个双向链表实现的栈结构。每个新注册的清理函数被推入栈顶，销毁时从栈顶依次弹出并执行。这种设计保证了嵌套资源的安全释放——如果A依赖B，那么B必须先于A被释放。

2. **状态机**：`PENDING → RUNNING → SETTLED → UNLOADING → DISPOSED`。状态转换严格控制，防止重复销毁。

解释一下**状态机**：
- **通俗说**：就像你玩游戏时的角色状态——"站立→行走→跳跃→攻击"。你不能从"站立"直接跳到"攻击"，必须经过中间状态。状态机就是一套规则，规定了哪些状态可以转换到哪些状态，确保系统行为可控、可预测。
- **专业说**：状态机是一种数学模型，由一组状态、一组转移函数和初始状态组成。在DeepSeek Harness中，Fiber的状态机确保了资源生命周期的严格管理——每个状态都有明确的进入条件和退出动作，防止竞态条件和资源泄漏。

### Events：响应式协效应的"调度引擎"

Events是实现响应式的核心。监听器随Fiber自动注册和销毁，事件分发支持多种策略。

解释一下**事件分发**：
- **通俗说**：就像公司里的公告系统。当有重要消息时，老板会通知所有员工。但不同的消息有不同的处理方式——有些需要所有人同时处理（并行），有些需要按顺序处理（串行），有些只需要第一个人处理完就结束（bail）。事件分发就是决定"如何把消息传递给监听者"的策略。
- **专业说**：事件分发是一种发布-订阅模式的实现。在DeepSeek Harness中，Events模块管理事件的注册、触发和监听器的执行策略。五种调度模式分别对应不同的并发控制需求，确保事件能够高效、安全地传递。

```typescript
export type DispatchMode = 'emit' | 'parallel' | 'serial' | 'bail' | 'waterfall'
```

五种调度模式：

|| 模式 | 行为 | 典型场景 ||
||------|------|----------||
|| `emit` | 同步执行，不等待结果 | UI状态更新 ||
|| `parallel` | 并发执行，等待全部完成 | 多文件读写 ||
|| `serial` | 顺序执行，遇到bail值停止 | 权限检查链 ||
|| `bail` | 同步执行，返回第一个非空值 | 配置查找 ||
|| `waterfall` | 洋葱模型，支持next()委托 | 工具执行管道 ||

解释一下**洋葱模型**和**waterfall模式**：
- **通俗说**：想象你在剥洋葱——从外到内一层一层剥。每一层都可以决定"要不要继续往里剥"。在编程中，这就像一条流水线：第一个人处理完，传给第二个人；第二个人可以选择自己处理完就结束，或者继续传给第三个人。这就是waterfall模式——每个监听器可以决定是否继续传递事件给下一个监听器。
- **专业说**：洋葱模型是一种中间件模式，类似于Express/Koa的中间件机制。每个监听器接收一个`next`函数，调用`next()`将控制权传递给下一个监听器，否则中断链条。这种设计允许监听器之间进行协作和拦截，非常适合构建可组合的处理管道。

**Context Filter**：这是dsh-scope包的核心机制。它实现了论文中的"协效应规范"——组件声明所需依赖，运行时据此分类上下文变化。

解释一下**Context Filter**：
- **通俗说**：就像你去参加一个派对，门口有保安检查你的邀请函。保安会看你的邀请函上写着什么——如果写着"允许进入VIP区域"，你就能进；如果只写着"普通区域"，你就只能在大厅活动。Context Filter就是这个"保安"，它根据组件声明的需求（邀请函）来决定组件能访问哪些资源（能进哪个区域）。
- **专业说**：Context Filter是一个谓词函数，接收Context对象作为参数，返回布尔值表示当前上下文是否满足条件。在DeepSeek Harness中，Scope使用Context Filter来实现层级隔离和权限控制，确保每个组件只能访问其被授权的资源。

### Scope：上下文隔离的"围墙"

Scope实现了"向下继承、向上传播"的层级关系。

想象一个大公司：总部（root scope）可以看到所有部门的数据，但每个部门（agent scope）只能看到自己的数据。不过，当某个部门发生重要事件时，总部可以收到通知。

解释一下**Scope**和**层级隔离**：
- **通俗说**：就像你家里的不同房间——客厅是公共区域，所有人都能进；卧室是私人区域，只有家人能进；保险柜更是只有你有钥匙。Scope就是这种"房间隔离"机制，确保不同的组件只能访问自己被授权的资源。
- **专业说**：Scope是一种命名空间隔离机制，通过树形结构实现资源的层级可见性。子Scope继承父Scope的资源，但不能反向访问。事件可以通过"向上传播"机制让父Scope感知子Scope的变化，实现松耦合的通信。

```typescript
export function scopeTarget<T>(base: T, key: ScopeKey): Scoped<T> {
  return {
    [Context.filter](ctx: Context): boolean {
      const tag = scopeOf(ctx)
      if (tag === undefined) return true
      // 事件向上传播：监听者可以接收后代scope的事件
      for (let cursor = key; cursor !== undefined; cursor = scopeParents.get(cursor)) {
        if (cursor === tag) return true
      }
      return false
    },
  }
}
```

### Tool Calls：工具调用的"并发调度"

AI Agent的核心能力是调用外部工具。Tool Calls模块支持并发、取消、重试，并且结果必须有序提交给模型。

解释一下**Tool Calls**和**并发调度**：
- **通俗说**：想象你在厨房做饭，需要同时处理多个任务——切菜、煮饭、炒菜。你可以一个人按顺序做（串行），也可以请家人帮忙一起做（并行）。但不管怎么做，最后上桌的菜必须是完整的——不能因为并行处理就少了一道菜。Tool Calls就是这样一个"厨房调度系统"，确保多个工具调用能够高效执行，同时保证结果完整有序。
- **专业说**：Tool Calls模块管理AI Agent对外部工具的调用生命周期。它支持并发控制（有界池）、取消机制和重试策略，并通过Ordered Commit确保并发执行的结果按原始请求顺序提交，避免日志混乱和状态不一致。

关键设计：

1. **并发模式分类**：根据工具声明决定并发策略（exclusive vs parallel）。

解释一下**并发模式分类**和**Bounded Pool**：
- **通俗说**：想象你在餐厅点菜，厨房有多个厨师。有些菜需要独占一个厨师（比如做蛋糕），有些菜可以多个厨师一起做（比如炒青菜）。并发模式分类就是决定"哪些任务可以并行、哪些必须串行"的规则。Bounded Pool就像餐厅的座位数——即使有很多顾客，也只能同时服务有限的人数，避免厨房过载。
- **专业说**：并发模式分类基于工具声明的互斥性标记。Exclusive工具在同一时间只能有一个实例执行，Parallel工具可以并发执行。Bounded Pool是一个固定大小的线程池，限制同时执行的任务数量，防止资源耗尽。

2. **Bounded Pool**：并行调用使用有界池，限制同时执行的调用数。

3. **Ordered Commit**：即使并发执行，结果也按模型顺序提交，确保日志一致性。

解释一下**Ordered Commit**：
- **通俗说**：想象你在超市排队结账，收银台有多个收银员。你把你的商品分成几堆，分别给不同的收银员处理。但最后你的购物小票上，商品的顺序必须和你放进购物车的顺序一致——不能因为并行处理就乱了顺序。Ordered Commit就是这样一个"排序系统"，确保并发执行的结果按原始请求顺序提交。
- **专业说**：Ordered Commit是一种并发控制机制。每个工具调用被分配一个序列号，并发执行后，结果按照序列号排序并依次提交。这保证了会话历史的线性一致性，即使底层操作是并发执行的。

### Session：会话持久化的"不可变日志"

会话历史是AI Agent的核心状态。Session采用append-only设计，事件只能追加，不能修改或删除。

解释一下**Session**和**append-only设计**：
- **通俗说**：想象你在写日记——每天发生的事情都记录在当天的页面上。你不能回去修改昨天的日记，也不能撕掉某一页。这就是append-only设计：数据只能追加，不能修改或删除。这样做的好处是，历史记录永远可信，不会被篡改。
- **专业说**：Session是一个不可变的事件日志（Event Sourcing模式）。每个事件被分配一个递增的序列号，追加到事件列表中。这种设计保证了数据的完整性和可审计性，同时支持时间旅行查询——可以回溯到任意时间点的状态。

```typescript
export class Session {
  append(event: Omit<SessionEvent, 'seq'>): SessionEvent {
    const fullEvent = { ...event, seq: this.seq++ }
    this.events.push(fullEvent)
    this.emit('session/append', fullEvent)
    return fullEvent
  }
}
```

这就像银行的交易流水——每一笔交易都记录下来，任何人都不能篡改历史。

读完此文与此代码，有三悟：

**其一，抽象之力量。** 效应与协效应本为静态分析工具，作者将其提升为运行时机制，赋予动态组合之形式基础。此乃**从静态到动态之范式跃迁**。

### 学术研究方向

解释一下**形式化验证**和**元理论性质**：
- **通俗说**：想象你在建一座桥。传统方法是画图纸、做模型、测试承重——这是"工程验证"。形式化验证则是用数学公式证明"这座桥在任何情况下都不会垮"。它不是通过实验来验证，而是通过逻辑推理来保证正确性。元理论性质就是这些数学证明要验证的"安全保证"——比如"无论怎么加载插件，系统都不会崩溃"。
- **专业说**：形式化验证是使用数学逻辑来证明软件系统满足特定规范的技术。Coq和Isabelle是两种交互式定理证明器，允许开发者构建严格的数学证明。元理论性质是指关于系统本身的理论性质——保持性保证操作不破坏已有保证，时间可组合性保证卸载时环境恢复，空间可组合性保证依赖解析正确，进展性保证系统不会死锁，汇合性保证并发操作最终一致。

**类型系统扩展。** 可逆效应如何融入现有类型系统？Haskell的Effect Systems、Scala的ZIO、TypeScript的Effect-TS，各有其道。你可以探索如何将可逆效应与这些系统结合，提出更通用的类型级表达方式。

解释一下**类型系统**和**Effect Systems**：
- **通俗说**：想象你在写一篇文章，类型系统就像是一个"语法检查器"——它会告诉你"这个句子不通顺"或者"这个词用错了"。在编程中，类型系统会在编译时检查你的代码是否有错误，比如"把字符串传给一个需要数字的函数"。Effect Systems是类型系统的扩展，它不仅检查值的类型，还检查副作用的类型——比如"这个函数会修改文件吗？""这个函数会发送网络请求吗？"
- **专业说**：类型系统是一种形式化方法，用于对程序的值进行分类并强制执行特定的操作。Effect Systems（效应系统）是类型系统的扩展，通过给类型标注效应信息来追踪副作用。例如，Haskell的`IO a`类型表示一个会产生副作用的操作，Scala的ZIO和TypeScript的Effect-TS则是更现代的实现，提供了更丰富的组合子和类型级推理能力。

**组合性理论。** 论文讨论了局部时空可组合性如何推广至全局，但具体条件未明。你可以研究：什么条件下，局部可组合性保证全局可组合性？这对分布式系统、微服务架构有深远意义。

解释一下**组合性理论**和**局部/全局可组合性**：
- **通俗说**：想象你在搭积木——每一块积木都是"局部可组合的"，它们可以互相连接。但如果你搭了一座很高的塔，可能会因为重心不稳而倒塌。这就是"全局可组合性"的问题：即使每个小块都能稳定连接，整体结构也可能不稳定。组合性理论研究的就是"什么样的规则能保证局部稳定就能全局稳定"。
- **专业说**：组合性是计算机科学中的一个核心概念，指系统的组件可以独立开发然后组合成更大的系统，且组合后的系统保持预期的性质。局部可组合性指单个组件满足某些性质，全局可组合性指整个系统满足这些性质。组合性理论研究从局部到全局的推导条件，对模块化设计、分布式系统正确性证明至关重要。

**性能模型。** 可逆效应引入了额外开销——每个副作用需携带逆操作，运行时需累积和恢复。你可以建立性能模型，分析开销边界，提出优化策略。

解释一下**性能模型**：
- **通俗说**：想象你在开车——每踩一次油门，车就会加速；每踩一次刹车，车就会减速。但如果你想知道"这辆车的油耗是多少"，你需要建立一个模型来预测：在不同的速度、路况下，油耗会是多少。性能模型就是这样一个"预测工具"，它帮助你理解系统的运行成本，从而做出优化决策。
- **专业说**：性能模型是对系统资源消耗（时间、空间、网络等）的数学描述。对于可逆效应，性能模型需要分析：追踪变换的开销、累积器的大小、恢复变换的时间复杂度等。通过建立精确的性能模型，可以识别瓶颈、指导优化，并给出理论保证——"在最坏情况下，开销不超过X"。
